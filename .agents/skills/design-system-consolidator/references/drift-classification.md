# Classify before correcting

| Classification | Evidence to seek | Response |
| --- | --- | --- |
| Intentional variation | Documented density, platform, prominence, content, or state requirement | Preserve it; express it as a shared variant only when the contract is genuinely shared. |
| Accidental drift | Active consumer bypasses an established role/component without a supported reason | Correct the shared cause and migrate affected consumers within scope. |
| Outdated usage | Deprecated component/token or a consumer still using an older documented contract | Follow the named replacement and check compatibility; age alone is not proof of breakage. |
| Missing system capability | Repeated real need cannot be expressed by the current supported system | Propose the smallest role/variant that represents it; do not force a misleading existing token. |
| Unknown intent | Similarities or differences without enough governing evidence | Keep as a candidate; inspect history/docs/consumers or ask only if the unresolved choice blocks the requested change. |

Check visual, behavioral, token, and component-API divergence separately when they have different causes. A deliberate product exception is not accidental drift merely because it diverges from a library default.

Preserve primitive values where the system defines them. Prefer semantic roles at consumers when those roles exist; do not create a second naming scheme solely to conform to a generic recipe. Frequency supports prioritization, not authority.
