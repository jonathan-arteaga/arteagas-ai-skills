# Broad terminology changes

Before broad renaming, map the product concepts, current labels, relevant contexts, preferred labels, and deprecated alternatives. Distinguish synonyms from concepts that only appear similar.

Produce a glossary and migration map: concept, preferred term, previous term, UI/resource locations, locales, and dependencies. Include exceptions for platform conventions and genuinely different behavior.

Inspect navigation, settings, onboarding, toasts, errors, confirmations, help text, and resource consumers within the requested scope. A label change must not silently rename persisted fields, API contracts, analytics events, URLs, or database records. List those as separate compatibility work when actually implicated.

Use existing decisions when available. Ask for product ownership input only when two meanings remain plausible and choosing one would change behavior or user expectations. Do not wait for approval of routine consistency fixes already authorized.

After authorized edits, search for remaining deprecated terms, classify intentional occurrences, verify resource references, and report unresolved locales or consumers. Do not remove historical terms from unrelated content merely because a new UI term was selected.
