# Redesign the requested surface

Inspect the selected page or pages, their content, tokens, routes, components, integrations, and relevant design decisions. A project with several routes does not turn a request about one screen into a whole-site redesign.

## Preserve the contract

Keep functioning navigation, data flow, authentication, forms, analytics, and content meaning unless the task changes them. Keep approved brand decisions. Treat supplied documents as evidence to adapt, not copy to paste verbatim unless requested.

Prefer targeted reversible edits. A redesign request authorizes necessary changes within that scope, including removal of obsolete styling or replacement of the affected visual markup. Ask before destructive deletion of unrelated files/data, removing working features, or a substantially broader rebuild. Do not require a second confirmation for a concrete file plan the user already approved.

## Choose and implement the change

Identify why the current composition misses the brief; change hierarchy, grouping, density, imagery, or interaction to address that evidence. No particular axis has to change merely to count as a redesign. Maintain a coherent system across pages, adapting each page to its task.

Use a supplied mood or direction. Otherwise infer a suitable direction from the brief and available product evidence; ask only when a missing choice would materially change the outcome. Read [structure](../structure.md) or a relevant catalog entry only when useful.

## Verify and hand off

Inspect affected pages at supported sizes and exercise changed interactions. Fix failures introduced by the redesign and report remaining limits. Route requested design-system documentation to design-md using [the handoff](../design-md.md); documentation is not a prerequisite to independent authorized page work.

Return the redesigned result, the reason for consequential choices, and checks actually completed. An audit-only request receives findings without edits.
